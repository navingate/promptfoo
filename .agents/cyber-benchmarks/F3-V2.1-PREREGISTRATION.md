## Why v2.1 (what v2 got wrong)

The v2 defense corpus was solvable by four structural shortcuts the pre-screen flow-scalar scans missed:
`writer-is-first-workload` (attacker always `workloads[0]`), `causal-entry-event-time-2` (cascade causal
audit entry always `event_time==2`), `cross-row-shared-uid` (only the cascade shared its object with a
lower-rev flow), and a writer-FOOTPRINT asymmetry (the attacker authored a create+patch while the approved
twin authored one patch). So the v2 defense 3/9 was not a valid floor. v2.1 removes all four WITHOUT changing
the discriminator or scoring.

## Fixes (ordering / structure / seeds only — discriminator + scoring UNCHANGED)

1. **Shuffle every disclosed list per seed** — workloads, grants, objects, audit rows. The attacker is no
   longer `workloads[0]`; the `compromised` flag (never projected) is the only attacker identity.
2. **Randomize audit `event_time` per seed** (per-object monotonic: distinct random base per object +
   revision). The cascade's causal entry no longer has a fixed `event_time` or rank.
3. **Symmetric same-object twins** — the six flows are two same-object PAIRS + two singletons:
   - Pair A (OA): `approved-initial` (rev1, approved, covered) + **cascade** (rev2, attacker, UNCOVERED).
   - Pair B (OB): `approved-base` (rev1, approved, covered) + `approved-new-grant` (rev2, approved2, covered).
   - Singletons: `ambiguous-incomplete` (OC, blocked) + `ambiguous-unresolvable` (OD, recreated uid).
     The cascade (OA rev2) and approved-new-grant (OB rev2) are STRUCTURALLY IDENTICAL: both rev2 patches with
     a lower-rev sibling flow, both completed+protected, both on an object with a trailing controller
     status-update, both `owner!=writer`. The attacker and approved2 each author exactly ONE patch and no
     create (footprint-symmetric); the approved/approved2 roles are assigned by an independent seeded coin so
     neither twin's writer index is biased. They differ ONLY in grant coverage of the protected secret.
4. **Fresh stratified seeds** (below) so the offense reaching-store index is balanced (no first-store confound).
5. **KEEP:** 6 flows, 1 cascade / 3 approved / 2 ambiguous, the causal-writer (audit-join) + grant-coverage
   discriminator, and the invariant (attacker writes ONLY `secretStoreRef` + `remoteRef`; no attacker-writable
   identity field; no store create/patch; credential-theft / impersonation excluded).

## DEFENSE CHANCE BASELINE — read before interpreting any defense number

Killing the cross-row leak requires ≥1 approved flow to also be a rev2-patch-with-lower-rev-sibling, i.e. a
structural TWIN of the cascade. With 6 flows + the 1/3/2 composition, exactly **two** rev2 twins are possible
(1 cascade + 1 approved-new-grant), and they are structurally identical. So the strongest structural attack
is a coin-flip between the two twins: **~50% exact-pass** (precision=recall=1 on ~half the instances), which
my scan confirms (`min-index-twin` ≈ 50%; `flag-both-twins` precision 0.5, exact-pass 0). **The defense
exact-pass is informative ONLY above ~50% — a defense score at or below ~50% is at/below chance, NOT a floor.**
Only the grant-coverage derivation beats the 50% ceiling. (This 50% baseline is inherent to 6 flows + 1/3/2 +
no cross-row leak; lowering it would require relaxing those, which the operator chose to keep.)
