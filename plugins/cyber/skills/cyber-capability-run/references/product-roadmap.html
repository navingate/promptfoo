The opportunity

Why this benchmark exists

Enterprises are beginning to deploy autonomous AI agents wired to real tools and credentials — CI systems, directories, cloud IAM, data stores. Two questions follow, and neither is answered today: what is the offensive blast radius of such an agent, and is a given model safe to deploy for a given role?

Public benchmarks like Cybench measure elite capture-the-flag puzzle solving on static, publicly-known, and bit-rotting tasks — valuable, but they neither reflect realistic multi-stage enterprise offense nor speak to deployment safety. Our benchmark is built to be different on four axes that make it defensible and, ultimately, saleable to frontier labs and enterprise buyers:

01

Enterprise-realistic

Multi-stage attacks across observability, CI, directory, federation, IAM, KMS and tenant data — the estate agents actually touch.

02

Contamination-resistant

Every run is a freshly generated instance with fresh secrets, so a model that memorized the benchmark gains nothing.

03

Depth-measured

Per-hop scoring reveals where a model cliffs, not just pass/fail — a capability horizon, not a single bit.

04

Profile-scored

Results reported by deployment profile: a model may be safe as a read-only assistant yet unsafe as a privileged agent.

The product

One offensive flagship, six safety tracks

The benchmark has two parts: a flagship offensive-capability track that measures how deep an agent can autonomously compromise an estate, and a set of deployment-safety tracks that measure whether the deployed system can be trusted with tools and data.

Track A — Offensive capability

Flagship

A family of frontier chains, each a realistic enterprise kill-chain the agent must reason through end-to-end. Measures capability and blast radius, and where a model's reasoning runs out.

Answers: "Can the agent compromise the environment when instructed to?"

Tracks B–F — Deployment safety

  • BDirect-misuse resistance — unauthorized actions on explicit request.
  • CPrompt-injection resistance — hijack via tickets, logs, docs, emails, tool output.
  • DAuthorization compliance — respecting user, tenant, data and approval boundaries.
  • EContainment effectiveness — which scoped-credential, segmentation and egress controls stop it.
  • FBenign utility — still doing legitimate work without excessive refusal.

Every result is reported per deployment profile — the same model can pass one and fail another:

Read-only assistant→ Developer agent→ Operations agent→ Security agent→ Privileged autonomous agent
How results surface

The benchmark runs through promptfoo as the system of record, so every run lands in promptfoo view as a grid: tasks as rows (tagged by track), models as columns, pass/fail per cell with the full agent transcript on drill-down. The provider emits named scores — hops reached and exploit-demonstrated — so the grid ranks and aggregates them like any metric. The two things a flat grid can't draw — the per-hop horizon curve and the profile × track matrix — stay as a separate report layer built on the same run data.

How we measure success

Claims we can defend

Independent review sharpened not just the design but the language. We report bounded, evidence-backed claims — never absolutes.

"Contamination-resistant"Resistant to memorized instance solutions; applying a learned strategy to a novel instance is legitimate generalization.
"No unintended shortcut exists"No shortcut known within the defined threat model after automated, adversarial and independent validation.
"Failures are capability gaps"An observed performance gap for that model-and-agent configuration under the tested budget and tools.
"Harder than Cybench"A credible path to harder than individual Cybench tasks — the flagship of a larger suite, shown empirically.
"Safe for profile X"Meets the defined acceptance criteria for profile X under the tested threat model, configuration and model version.

Statistical honesty carries through to safety: a clean run bounds only that test family's failure rate, under independence assumptions — it is not an enterprise breach probability, since real attacks are correlated. We report the evidence and its scope, never a single "safe" number.

Risks & dependencies

What could slow us, and where we rely on others

HighDifficulty is empirical
"Only a frontier model solves it" can only be confirmed by running one. The design aims high; calibration may require turning a knob after the first frontier run.
HighGenerator engineering
Held-out families plus a large-seed validation harness are a real build, not a one-shot. Staging contains the risk but not the effort.
MedModel & compute access
Calibration and safety claims need access to strong models and sandbox compute; throughput here paces P1–P4.
MedSafety claims need controls
A defensible "safe" statement rests on deterministic controls that block critical actions, not model refusal alone — which expands scope into the deployment configuration itself.
MedValidation is off-box
The team validates through sandbox runs rather than local testing, so each stage depends on an execution loop against the environment.
