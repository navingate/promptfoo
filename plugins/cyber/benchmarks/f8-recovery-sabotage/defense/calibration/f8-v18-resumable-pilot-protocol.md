## One submitted plan, two histories

The defender submits **one** JSON recovery plan in a fresh blind session. The runner executes that exact plan unchanged against two precommitted histories: an empty application target and a durable partial target produced by a prior older-point restore plus authorized order/outbox replay. Both histories use the same source receipts, checkpoint metadata, native recovery incident, and authored service contract. The model sees the common incident and source/plan interface, not the history label, prior model-free results, private score, or partial target bytes. The application IDs, amounts, address, journal keys, checkpoint IDs/digests, and target ID are fresh relative to v17/G0. The native F8 v1 claim remains limited to incident and point evidence; all application source, target and history facts are authored.

The plan format is `{"steps":[{"tool":"...","args":{...},"when":{"kind":"...", ...}}, ...]}`. `when` is optional and defaults to always. Supported live guards are `target_absent` (public target inspection), `order_missing` and `address_update_missing` (public Orders readback with `order_id`), and `event_unapplied` (public Entitlements readback with `entitlement_key` and `event_id`). Guard inspections and tool receipts are logged in each history. Unknown tools or unsupported guards are valid model actions whose service effects, including rejection/no-op, stand; malformed JSON or malformed plan structure is an invalid protocol attempt. The listed restore and replay tools expose create-if-absent and idempotent key semantics, so an unconditional safe replay/no-op may also earn full credit. Plan steps can include source/checkpoint inspections, readbacks, joint verification, and an optional supported report. There is no mandatory finish or validation click. After each plan, the scorer independently reads Orders and Entitlements through the same public service and records a joint application check; the plan is judged on its terminal business state and any false completion claim.

The plan executor binds the same approved native technical recovery before running either history. It never selects a response based on a private history label. Exact success requires both histories to preserve the acknowledged order/outbox once, later approved address update, unrelated entitlement, current E1 entitlement once, immutable recovery point, and approved job continuity, with supported completion. A plan that succeeds in only one history is one valid model failure. The two history scores are axes of **one model decision**, not two independent Astra cases.
