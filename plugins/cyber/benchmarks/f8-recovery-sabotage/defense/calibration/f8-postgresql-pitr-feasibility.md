# F8 PostgreSQL PITR feasibility: negative finding

**Disposition:** Close at feasibility. No scratch cluster, fixture, Astra call, or GLM call was started. The v20 **2/2 valid exact** pilot and v21 **zero-model** regression remain separate.

PostgreSQL 17.7 Homebrew provides `postgres`, `initdb`, `pg_ctl`, `pg_basebackup`, and `psql` at `/usr/local/opt/postgresql@17/bin`. The current user can own a disposable directory under `/private/tmp`, which had about 40 GiB free during the read-only check. An isolated drill could use a new data directory, a private Unix socket directory, explicit client connection options, and `listen_addresses=''` so it accepts no TCP connections. These are feasibility observations; no connection to an existing database or service was made. [PostgreSQL's connection settings](https://www.postgresql.org/docs/17/runtime-config-connection.html) document socket-only operation, and [`pg_basebackup`](https://www.postgresql.org/docs/17/app-pgbasebackup.html) supports a physical base backup with streamed WAL.

PostgreSQL [PITR documentation](https://www.postgresql.org/docs/17/continuous-archiving.html) states that base backup plus WAL replay can stop at an earlier consistent point and that physical recovery restores the **entire cluster**, not selected rows. [Recovery target settings](https://www.postgresql.org/docs/17/runtime-config-wal.html#RUNTIME-CONFIG-WAL-RECOVERY-TARGET) allow a named, time, transaction, or LSN stop point. From those mechanics, a restore before an erroneous committed update would also omit a later approved write, while replay through both would retain the error. This is a mechanism inference, not an observed F8 incident or an executed PostgreSQL result.

The proposed one-error/one-later-approved-write business obligation has an ordinary safe path: retain the later write by recovering through both transactions and make an authorized scoped correction to the erroneous update. With the error and repair target already identified, this is the same blanket-rewind versus scoped-forward-repair invariant exercised by F8 v16, where Astra was **2/2 valid exact**. A real PostgreSQL replay would add product execution evidence but no distinct defender decision or credible floor. A new F8 candidate needs source or replay evidence for a different consequential invariant before another model-free build or blind pilot. Native F8 v1 supplies only the recovery incident and point; all proposed ledger transactions and authorizations would have been authored.
