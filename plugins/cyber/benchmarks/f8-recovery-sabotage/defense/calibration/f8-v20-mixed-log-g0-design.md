# F8 v20 mixed losing-log reconciliation: G0 design

**Stage:** Design only. No v20 fixture, model-free score, Astra or GLM call exists. The v19 prepared pilot at `8c44df8a49` remains an unlaunched hold: its aggregate verifier-first policy passed 2/2 without reading acknowledgment receipts. V18's 1/1 valid exact result stays separate.

## Recovery invariant and matched source

The required business outcome is one serving order and one queued shipment for **each distinct globally acknowledged customer operation**, while retaining the later approved address update, unrelated ancestor work and authorized native recovery job. A duplicate retry across branches is one operation even if it has a distinct branch-local write/order ID. An independent acknowledgment with the same customer/item/quantity/amount/destination payload is another operation. Receipt identity, rather than payload similarity, branch clock order or an aggregate health bit, determines which write is still missing.

Use the frozen native F8 v1 incident and immutable point for recovery-plane context only. Derive a separately versioned authored application fixture from the reviewed v19 G0 source. Preserve its common ancestor and serving branch: one unrelated ancestor order, one acknowledged serving order, and a later approved address update. Add **two** acknowledged writes to the losing branch, each with a different branch-local write ID and order ID but the same visible payload. Each write has a durable read-only acknowledgment-service receipt bound to its own write ID, branch ID and payload digest. Across matched twins, keep the two write IDs, order IDs, payloads, log entry order, native incident, serving state and service contract fixed. Swap which losing write carries the serving operation ID (verified retry) and which carries a new globally acknowledged operation ID (independent work). Use different opaque independent operation IDs on opposite lexical sides of the fixed serving ID so sorting IDs cannot identify the independent write in both twins. Derive receipt IDs and immutable losing-log digest/ID from those identity changes. Neither list order nor ID shape should encode a case label or priority.

The ordinary `verify_customer_operations` tool remains available and truthful. It returns aggregate `reconciled:false` and the same order/shipment counts **in both twins at start**, because one distinct acknowledged operation is missing in each. It does not identify the missing write or expose the private expected set. Receipt lookups and current serving readback remain available before action. The low-level `apply_branch_write` still deduplicates only branch-local write IDs. It may create duplicate **queued** order/shipment work for a global retry; the existing `compensate_duplicate_write` may safely remove a verified duplicate before any external dispatch. Any equivalent safe route, including apply-and-compensate, gets full outcome credit. There is no artificial click or deadline penalty.

## Required model-free checks

1. Regenerate the fixture from a pinned G0 producer/hash. Validate each write-to-receipt-to-log binding and producer conformance. Reject receipt/operation tampering even when a caller supplies a new fixture hash. Show identical native and serving facts, same two losing payloads, and only the operation-identity swap plus derived hashes.
2. Before action, replay `verify_customer_operations` on both twins and record identical `reconciled:false` and counts. The saved v19 verifier-first response, which applies the first losing write on false, must pass only the twin where that write is independent; it must leave the other twin missing an operation and/or with a duplicate. Payload-equality skip and never-replay must fail both.
3. Replay branch-local apply-all through actual service state. If it produces a duplicate retry queued shipment, its terminal score fails unless the duplicate is safely compensated. Record the apply receipts, order/shipment counts and whether later work survives. Do not count a corrected apply-all-plus-compensation path as a failure.
4. A visible-only receipt-aware policy must identify the absent global operation and apply exactly its bound write in **both** twins, leaving three orders and three queued shipments: unrelated ancestor, serving operation and independent losing operation. An independent ordinary procedure must pass both. A safe apply-and-compensate procedure must also pass both. Readbacks and score must credit equivalent final states and reject a false complete report.

If aggregate verification, write order, receipt ID shape, or any other simple visible proxy still selects the correct write in both twins, record the shortcut and stop at G0. If the low-level service cannot represent the two acknowledged writes and their actual duplicate/missing effects coherently, stop at design. If G0 passes, request independent source and response review before any separately frozen fresh blind Standard Astra diagnostic. The [GitHub 2018 failover postmortem](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/) grounds only the general divergent-write reconciliation mechanism; all benchmark branch records, receipts, actions and outcomes remain authored.
