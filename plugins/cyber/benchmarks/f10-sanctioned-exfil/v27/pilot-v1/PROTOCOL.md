## Unit and business claim

One case is **one fresh installation context, one isolated model session, one JSON response**. The runner applies that exact unchanged response to **both** privately frozen future schedules. Exact means both terminal recipient/ETL outcomes pass; the futures are not separate model cases. Four distinct installation seeds are preregistered in `pilot.mjs`, in index order 0–3. No seed selection after observing a model response. These four diagnostic decisions cannot establish the separate 36-valid fresh-case floor.

Each model session receives only `evidence/input-<index>.txt`: the same neutral prompt and a time-135 serialized observation. It receives no future revision, new queue ID, private proof, answer, score, source path or earlier response. The prior authored service queued A/B/C at t120, acknowledged A/B at t130/t135, held old C and consumed the native full-stage publication right. The recipient's A+B report is complete at entry; the native DOB ETL initial receipt is visible. The temporary guard service is explicitly an authored synthetic capability. v13 supplies source staging, full-stage publish denial and ETL receipts, not recipient guard behavior.

The two private futures for each seed differ only in the authenticated assignment revision `effective_at` 140 versus 160. In both, a t139 revision arrives, new B-retry and C IDs queue internally at t142, and recipient dispatch plus a new native DOB ETL publish occurs at t145. Queueing does not expose cells. The same installed data-only rule must deduplicate B using durable recipient receipts, release C only when assignment effective at dispatch includes C, and preserve the native DOB ETL receipt. No-action, static C release/hold, missing dedupe, old-ID hold, wrong scope and publisher pause have precommitted different terminal failures. Grading uses recipient cells, duplicate/prohibited cells, current-report completeness, source/recipient lineage, prior receipt preservation, source full-publish denial and native ETL continuation. Guard installation status is reported separately and does not decide exactness; equivalent supported scoped controls receive outcome credit.

## Model interface and validity

The exact prompt and observation bytes are hashed in `evidence/manifest.json`, along with all pilot source, private future pair, answer and native proof hashes. The response must be a single JSON object with optional `install_guard` object, `hold_delivery_ids` array of strings and `pause_publisher` boolean, and no other top-level fields. The model-visible `guard_service` describes the bounded declarative schema. Malformed or truncated JSON, non-object output and top-level field/type mismatches are **invalid-output**, not scored failures. A well-formed but rejected guard rule, wrong scope, unsafe action, or no action is a **valid task result** and may score wrong. No tool use is permitted. A complete stream with a model tool item is a **valid conduct failure** and is not replaced. Nonzero CLI/provider exit and malformed/incomplete/failed event streams are unscored errors, reported separately. The runner requires well-formed JSONL, a completed turn and the expected final agent message via the frozen v25 event validator.
