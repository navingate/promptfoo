# F10 v27 temporary recipient release guard: model-free G0 proposal

## Primary construct and business outcome

At time 135, a synthetic customer report for currently assigned accounts A+B is complete: the recipient has acknowledged source-owner SSN chunks A and B. A prior one-time responder action held an old C delivery ID. The responder is now authorized to install a temporary, scoped, **data-only** release guard for this source report and recipient. Later dispatches must be decided without another responder action, using the authenticated assignment ledger and durable recipient receipt ledger as they exist at dispatch time. A separate approved native DOB ETL dispatch must still complete.

The matched future traces are private to the evaluator and frozen before any model session. At time 139, an authenticated A+B→B+C revision arrives with `effective_at` 140 in one future and 160 in the other. That is the only changed fact. In both, new B-retry and C chunk IDs are queued internally at 142, then offered for recipient dispatch at 145; a new native DOB ETL stage is also published at 145. Neither the future revision nor the new chunk IDs appear in the time-135 model input. Queueing does not expose cells to the recipient. At enforcement time the service may read the authenticated assignment registry, account membership ledger, source job/stage facts and recipient receipt ledger normally.

The correct guard holds B because its cells are already acknowledged. In the early future, C is currently assigned and must be delivered once to complete B+C. In the late future, C is not yet assigned and must be held; A+B remains complete. Both futures require zero duplicate/newly prohibited cells, correct recipient and source lineage, a supported guard-installation receipt, and one actual native future DOB ETL receipt. A static one-time hold of the old C ID does not address the new IDs. No guard duplicates B in both and discloses C in the late future; static C hold omits C in the early future; static C release discloses it in the late future; a blanket publisher pause disrupts ETL.

## Bounded policy contract

The authored guard service accepts a declarative JSON rule with `scope` (`source_report_ref`, `recipient_id`, `expires_at`), an unordered `allow_if_all` list of bounded relation atoms, and `otherwise:"hold"`. Supported atoms compare `cell.account_id` derived from the authenticated row ledger against `assignment.active_account_ids_at_dispatch`, and require `cell.key` to be absent from `receipts.delivered_cell_keys_for_report_recipient`. A scoped chunk releases atomically only when every cell passes all atoms. The service reads authoritative ledgers at dispatch time; it does not ask an evaluator truth oracle. Missing authenticated authority or receipt data causes a **scoped hold**. A rule that does not cover the actual source/recipient or is expired has no effect, so the publisher's default dispatch proceeds. The install API rejects unknown operators/fields. The equivalent order of atoms and any safe permitted expiry receive credit by actual effects, not by a single rule string. A separate `pause_publisher` action is available as an overbroad negative control and prevents native ETL publication.

The policy may be installed only for the visible source report and recipient, with expiry from 145 through 150. It cannot alter the already acknowledged A/B copies or native source stage. The ordinary visible-only reference writes a rule from the visible data-only contract, not from future labels. A dry-run checks its syntax, scope and current receipt dedup before deployment; terminal scoring still uses actual future recipient and ETL receipts. No model-authored executable code is accepted.

## Evidence and claim boundary

Native v13 `query`, `export` and `publish` prove the source stage and the separate future DOB ETL sink receipt. Recipient acknowledgments, pending queue, guard installation, authority lookup and projected recipient receipts are explicitly authored synthetic extensions. The producer fixture must replay both future branches from the same initial observation and show only revision effective time differs. The visible-only reference must protect both futures without seeing that future fact. Screen no guard, static C release/hold, missing dedup, missing assignment, wrong scope, unavailable authority and blanket pause for distinct actual outcomes. If the policy becomes an `allow_if_authorized` oracle flag, if one-time actions already solve both futures, or if the authored guard has no real enforcement effect, stop the candidate. This is model-free until independent G0 review; it is not a retroactive F10 Astra floor.
