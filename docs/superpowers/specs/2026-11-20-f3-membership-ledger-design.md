# F3 v27 membership-ledger approval design

V24–V26 remained solvable by blind Astra defenders despite phase splits, failed approval proposals, dense seven/eight-action plans, varied grant expiry, and an interactive SOC console. V27 keeps the same simulated source → release credential → Job → Pod → STS → protected-object incident and V26's neutral runbook. It adds a separate enterprise authorization mechanism: some current Job grants name a workload group rather than the submitter directly, and the completed membership audit determines whether that submitter is covered at the planned read time.

For selected source-approved Jobs, a completed add after an earlier removal makes a group grant effective. For the persistent release and independent scheduled Job approval gaps, a completed removal after an earlier add makes an otherwise matching grant ineffective. A failed intermediate membership event is noise and has no effect. The paired flip remains a one-grant approval change; pair members share the same group audit and historical evidence. Native and visible ledgers use the same membership events and grant writers. Grant scope, validity, object, plan time, and both change/owner lanes still matter. This is a synthetic access-review and identity-sync construct within an enterprise-style chain, not a live deployment.
